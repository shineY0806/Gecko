# 星河中文网靶场抓取实战手册

> 目标：`http://127.0.0.1:3000`（一个小说站靶场，难度 **L4 · 风控站**，最高档）
> 工具：**Gecko** `range_crawler.py`（当时的 v3.8 / 引擎 3.7，本文同步更新到 v3.9）
> 成果：全站书目 20000 条、章节全文 499 篇、书评 480 条、目录 2101 条、点击榜 24 条
>
> 本文回答三件事：**思路是什么**、**一步一步怎么抓**、**用到了哪些爬虫技术、有没有借助别的工具**。
> 所有命令都可以直接复制运行（把端口换成你自己靶场的）。

---

## 〇、先说结论：这次抓取的骨架

整个抓取不是"开个爬虫让它跑"，而是**五步漏斗**，每一步都在回答一个具体问题：

| 阶段 | 要回答的问题 | 这一步的产物 |
|---|---|---|
| ① 侦察 | 这个站是什么、有哪些防护、暴露了什么 | 防护清单、URL 地图、密钥 |
| ② 找通道 | 哪条路能拿到数据、哪条路被堵 | 可用接口清单 |
| ③ 绕过对抗 | 被拦的原因是什么、能不能在工具能力内解决 | 移动端通道 |
| ④ 批量取数 | 怎么又快又不触发风控地把数据搬回来 | 原始响应（缓存） |
| ⑤ 清洗沉淀 | 怎么把 HTML/JSON 变成表格 | CSV 数据集 |

**核心判断**：PC 端主通道 `/api/*` 上了 JS 挑战（要 POST 提交计算题），工具当时只能发 GET，
**所以不硬碰，改走 PC 端没改造的移动端老接口 `/m/api/*`** —— 这是本次抓取最关键的一次转向。

## 一、目标画像：先看清楚对手是谁

### 1.1 探测性爬取（第一轮，先别想太多）

拿到一个陌生地址，第一步不要直接全站扫，先小范围摸底：

```bash
python range_crawler.py -u "http://127.0.0.1:3000" -d 1 --max-pages 30 \
  --comments --per-domain 3 --timeout 12 -o _probe
```

- `-d 1`：只爬种子页 + 它直接链出的一层，够看清结构
- `--comments`：抓 HTML 注释（靶场爱把提示藏在注释里）
- `--per-domain 3`：同时最多 3 个请求，别一上来就把人家打急了

**看到了什么**：30 个页面、2326 个 URL，站点名叫"星河中文网"，还带一个 `/range/level` 的难度切换页。
有 `/range/` 这种路径，基本可以确定是个**故意留漏洞的练习靶场**——那就一定要去读它自己写的说明。

### 1.2 读靶场自曝的三张页面

这类练习靶场通常会给自己配"说明书"，直接用工具抓下来读：

```bash
for p in range/level range/vulns range/scoreboard; do
  python range_crawler.py -u "http://127.0.0.1:3000/$p" -d 0 --max-pages 1 \
    --cache --timeout 12 -o _probe_info -q
done
```

`--cache` 会把响应正文原样存进 `_probe_info/.cache/*.json`（正文是 base64 字段 `body_b64`），
后面再慢慢解，不用重复请求站点。

**读出来的东西（决定性信息）**：

- `/range/level`：当前 **L4**，开启的防护有 14 项——
  `uaGuard`（UA 校验）、`refererGuard`（来源校验）、`session`、`rateLimit`（限速）、
  `cssScramble`（CSS 乱序）、`fontObfuscate`（字体反爬）、`signature`（接口签名）、
  `jsChallenge`（JS 挑战）、`fingerprint`、`captcha`、`riskEngine`（风险引擎）、
  `honeypot`（蜜罐）、`paywall`（付费墙）、`cursorSign`
- `/range/vulns`：**靶场自己列出了 15 条故意植入的漏洞**，等于给了答案的一半
- `/range/scoreboard`：审计板，能看到"我"被记了多少请求、被拦几次、风险分多少
  ——**这是后续调策略的仪表盘**，每次抓完都应该回来看一眼

> **方法论点**：练习靶场不是敌人，是老师。先找 `/range/`、`/admin/help`、
> `/robots.txt` 这类"管理员给自己留的入口"，能省掉大量盲猜。

## 二、信息收集：把站点主动交出来的东西全拿走

这一阶段的原则是：**只看不发、只取不猜**，全部用 GET。

```bash
for p in "robots.txt" "sitemap.xml" "feed/rss" "static/js/main.js" \
         "wwwroot.zip" ".git/config" "backup.sql"; do
  python range_crawler.py -u "http://127.0.0.1:3000/$p" -d 0 --max-pages 1 \
    --cache --max-body-mb 30 --timeout 12 -o _probe_info -q
done
```

结果逐条看：

| 目标 | 结果 | 拿到什么 | 对应技术 |
|---|---|---|---|
| `/robots.txt` | 200 | **Disallow 了 `/admin`、`/api/`、`/internal/`、`/range/`、`/m/`、`/backup`、`/wwwroot.zip`** | robots 信息泄露：不给爬的路径 = 后台地图，反而指明了 `/m/` 这条隐藏通道 |
| `/sitemap.xml` | 200（247KB） | 全站 book / chapter 的 URL 地图 | sitemap 种子发现（工具默认自动解析，无需额外参数） |
| `/feed/rss` | 200（14KB） | 结构化书目（标题/作者/简介），未鉴权 | RSS 订阅源是常被忽略的免鉴权数据出口 |
| `/static/js/main.js` | 200 | 硬编码 `SIGN_SECRET="xd9f2a7c4b1e8065"`，且 `md5()` 是占位实现 | 前端 JS 逆向：密钥不该出现在前端 |
| `/wwwroot.zip` `/../.git/config` `/backup.sql` | 200 | 全是 117~184 字节的**占位文件**，无真实泄露 | 备份文件探测——**要说清：没拿到就是没拿到，别硬凑** |

> **这一步的技术要点**：很多人以为信息收集是"扫目录"。其实优先级应该是
> **robots → sitemap → RSS → 前端 JS → 备份文件**，越靠前越省力、越不容易触发风控。

## 三、找通道：三次试探，一次转向

### 3.1 第一次试探：直接打 PC 端接口

```bash
python range_crawler.py -u "http://127.0.0.1:3000/api/books?page=1&pageSize=999999" \
  -d 0 --max-pages 1 --cache --per-domain 1 -o _probe_api -q
```

返回：`{"code":40301,"msg":"缺少 Referer"}`

**判断**：这**不是**签名拦我，**只是** Referer 校验。加上请求头再试：

```bash
python range_crawler.py -u "http://127.0.0.1:3000/api/books?page=1&pageSize=999999" \
  -d 0 --max-pages 1 --cache --per-domain 1 \
  --header "Referer: http://127.0.0.1:3000/" -o _probe_api2 -q
```

### 3.2 第二次试探：撞上 JS 挑战

加 Referer 后返回变成 **428**，页面内容是一道计算题：`144 + 590 = ?`
要求 POST 到 `/challenge/verify` 换会话。

**判断**：这是标准的 JS 挑战（jsChallenge）。当时的工具是**纯 GET 爬虫，不能发 POST 表单**，
这条主通道在工具能力内**走不通**。

> 这里顺手也试了无头浏览器渲染：
> `python range_crawler.py -u ".../chapter/545/1" --render stealthy --network-idle --wait-selector ".nr-content" -d 0`
> 浏览器能打开页面、能拿到那道计算题，但**提交答案需要 POST**，渲染解决不了"提交"这件事。

### 3.3 转向：移动端老接口（本次抓取的关键一招）

`robots.txt` 里那条 `Disallow: /m/` 提醒了我：PC 端上了全套防护，**历史上线的移动端接口往往没同步改造**。
这是真实世界里命中率很高的一条规律。

```bash
python range_crawler.py -u "http://127.0.0.1:3000/m/api/books?page=1&pageSize=999999" \
  -d 0 --max-pages 1 --cache --max-body-mb 15 --per-domain 1 -o _probe_m -q
```

返回：**200，12.6MB，`total=20000`**。

**一次请求拿到全站 20000 本书**，叠加了两个洞：

- V08：移动端老接口无鉴权（不用签名、不查 Referer）
- V03：分页参数无上限（把 `pageSize` 直接写成 999999，服务端照单全收）

顺带验证的端点：

| 端点 | 状态 | 说明 |
|---|---|---|
| `/m/api/books?page=1&pageSize=999999` | 200 | **全站书目**，一次到位 |
| `/m/api/chapter/:bookId/:idx` | 200 | **章节全文**（叠加 V04：付费墙只在前端隐藏，接口吐全文） |
| `/m/api/book/:id` | 200 | 单本详情 |
| `/m/api/rank`、`/m/api/user/:id`、`/m/api/search`、`/m/api/comments` | 404 | 未暴露，到此为止 |

> **方法论点**：被一条路堵死时，先枚举**同源的其他入口**——移动端 `/m/`、老版本 `/v1/`、
> 开放平台 `/openapi/`、小程序 `/wxapp/`、RSS、导出接口。它们的鉴权往往是后来才补的。

## 四、批量取数：怎么把数据又快又稳地搬回来

### 4.1 当时的做法（v3.8）：串行循环，一个 URL 启一次进程

全站 3227 万个章节不可能全抓，先按点击量取 Top 20 本书、每本前 25 章 = 499 条 URL，写进清单：

```bash
# _chapter_urls.txt 每行一个 URL
while IFS= read -r url; do
  python range_crawler.py -u "$url" -d 0 --max-pages 1 --cache \
    --max-body-mb 3 --timeout 12 -o _ch3000 -q
  sleep 0.1
done < _chapter_urls.txt
```

**结果**：499 条全部成功、0 失败，56.5 万字正文。但代价是：

- 启动了 499 次 Python 进程（每次约 1 秒冷启动）
- 串行 + `sleep 0.1`，实测 **QPS 仍达 0.81**，风险分从 30 涨到 45

### 4.2 现在的做法（v3.9）：一行命令搞定，且能压住 QPS

同样的 499 条，现在只需要**一次进程**：

```bash
python range_crawler.py --url-file _chapter_urls.txt -d 0 \
  --max-pages 600 --threads 4 --qps 2 --cache --max-body-mb 3 -o _ch3000
```

- `--url-file`：URL 清单文件，一行一个地址（`#` 开头是注释）
- `--qps 2`：**全局每秒最多 2 个请求**，不看线程数，直接压住风控最关心的那个指标
- `-d 0`：只抓清单里的地址，不去扩散

实测：`--qps 5` 抓 20 条用时 4.58 秒，不限速仅 0.82 秒——闸门是真实生效的。

### 4.3 HTML 常规页：常规 BFS 就好

首页、排行、分类、书籍页、书评页都是直连可抓的，交给 BFS 自动发现：

```bash
python range_crawler.py -u "http://127.0.0.1:3000/" -d 2 --max-pages 160 \
  --cache --comments --per-domain 2 --qps 2 -o _html3000
```

结果：136 个 200、24 个是 `/chapter/*` 被 428 挑战拦下的（v3.9 会把它们单独列进
`challenges.txt`，一眼就能看出对抗点在哪，不用再翻页面清单一条条猜）。

> **踩过的坑（值得记住）**：早期我用"在 8000 端口放个种子页，里面链到 3000 端口"的办法做批量分发，
> 结果 3000 的链接一条都没抓。当时误以为是"工具不跟随跨端口链接"，**实际不是**——
> 真实原因是 sitemap 自动发现的种子把 `--max-pages` 预算一次性吃光了，根本轮不到第二层。
> v3.9 已在这个场景主动告警：`提示: 种子（含 sitemap）共 N 个，已超过页面上限 M`。
> 规避办法：加 `--no-sitemap`，或直接调大 `--max-pages`，或用 `--url-file` 精准投喂。

## 五、清洗沉淀：把响应变成表格

工具 `--cache` 存下来的 `.cache/*.json` 里，`body_b64` 就是原始响应正文。
解出来转成 CSV，这一步**不发任何网络请求**，纯粹是本地解码：

```python
import json, base64, glob, csv
rows = []
for f in glob.glob('_ch3000/.cache/*.json'):
    d = json.load(open(f, encoding='utf-8'))
    if d.get('status') != 200:
        continue
    j = json.loads(base64.b64decode(d['body_b64']).decode('utf-8', 'ignore'))
    dd = j.get('data') or {}
    if not dd.get('content'):
        continue
    rows.append({'书籍ID': dd.get('bookId'), '章节序号': dd.get('index'),
                 '章名': dd.get('title'), '正文字数': len(dd['content']),
                 '正文': dd['content']})
with open('chapters.csv', 'w', encoding='utf-8-sig', newline='') as fh:
    w = csv.DictWriter(fh, fieldnames=list(rows[0].keys()))
    w.writeheader(); w.writerows(rows)
```

HTML 页面则用正则按 DOM 结构抽（例如书籍页目录是
`<tr><td>第N章</td><td><a href="/chapter/B/C">章名</a></td><td>N字</td></tr>`）。
工具自带的 `--select "字段名=CSS选择器"` 也能直接抽取结构化字段，输出到 `items.csv / items.json`。

**最终数据集**：

| 文件 | 条数 | 说明 |
|---|---|---|
| `books_全站书目.csv` | 20000 | 19 字段（书名/作者/分类/字数/章节数/点击/评分/简介…） |
| `chapters_章节全文.csv` | 499 | Top 20 本书 × 前 25 章，56.5 万字，0 失败 |
| `comments_书评.csv` | 480 | 用户/等级/时间/点赞/内容 |
| `catalogue_书籍目录.csv` | 2101 | 章号/章名/字数 |
| `rank_点击榜.csv` | 24 | 见下方"必须说清的一个现象" |

> **必须说清的一个现象**：`/rank?page=N` 的 49 个分页返回的内容**完全一致**（都是同样 24 条）。
> 我一度怀疑是被软封禁污染数据，于是**降速单独重抓 page=5 和 page=30 做对比**，结果仍然一致
> ——所以这是**站点分页参数无效**，不是封禁。点击榜只有 24 条有效数据，这是真实结果，不粉饰。
> 报"全绿"之前先证伪自己，这一步不能省。

## 六、用到了哪些爬虫技术（汇总）

| 技术 | 本次怎么用的 | 工具里的开关 |
|---|---|---|
| robots.txt 情报利用 | 从 Disallow 反推后台地图，发现 `/m/` | 默认抓取并列入 `robots_disallow` |
| sitemap 种子发现 | 拿全站 URL 地图 | 默认开启，`--no-sitemap` 关闭 |
| RSS / 订阅源 | 免鉴权结构化书目 | 直接当普通 URL 抓 |
| 前端 JS 逆向 | 从 `main.js` 读出签名密钥与占位实现 | `--cache` 存下 JS 再本地看 |
| 请求头伪造（Referer / UA） | 过 `refererGuard` | `--header`、`--user-agent` |
| 浏览器指纹伪装 | 让 TLS/HTTP 指纹像 Chrome | `--backend curl_cffi --impersonate chrome` |
| 无头浏览器渲染 | 拿 JS 执行后的 DOM、判定挑战题 | `--render dynamic/stealthy --network-idle` |
| **移动端老接口绕过** | 走 `/m/api/*` 绕开 PC 端签名与挑战 | 无需特殊开关，就是换 URL |
| **分页参数越权** | `pageSize=999999` 一次拉全量 | 无需特殊开关 |
| **付费墙绕过** | 接口吐全文，墙只在前端 | 无需特殊开关 |
| 并发与限速 | `--threads` + `--per-domain` + `--delay` | v3.9 新增 `--qps` 全局闸门 |
| 响应缓存 | 原始响应落盘，重复调试不再打扰站点 | `--cache` |
| 敏感路径标记 | `admin/`、`backup`、`.git` 自动标红 | 默认，输出 `interesting.txt` |
| HTML 注释提取 | 靶场藏在注释里的提示 | `--comments` |
| 自定义字段抽取 | `--select` 直接出 CSV | `--select "名=选择器"` |
| 表单/接口提交 | v3.9 新增，可打 `graphql`、登录、挑战 verify | `--method POST --data/--json` |

## 七、有没有借助别的工具？（如实回答）

**数据获取：全程只有 `range_crawler.py` 一个工具在发请求。** 没有用 curl、没有用 requests 手搓脚本、
没有借助任何外部抓取框架、没有人工在浏览器里点。

**配套用到的三样东西，都不发网络请求或只发本地请求**：

1. **`demo_server.py`**（工具箱自带的多线程演示服务器）——早期想在 8000 端口放种子页做批量分发。
   实测这条路被 sitemap 预算问题挡住了，最终没采用，改用 `--url-file`。
2. **本地 Python 解码脚本**——只读取工具自己 `--cache` 落盘的 `.cache/*.json`，把 base64 正文还原成 CSV。
   它**不发起任何 HTTP 请求**，属于数据清洗，不是抓取。
3. **`/range/scoreboard` 审计页**——这是靶场自带的仪表盘，我用工具抓它来看自己的风险分，属于正常侦察。

**没做到的部分（工具能力边界，不是站点不可破）**：

| 未拿到 | 原因 | v3.9 之后的状态 |
|---|---|---|
| `/api/*` 系列数据 | 要过 JS 挑战：POST 计算题换会话 | `--method POST --data` 已能提交；但**会话 Cookie 需人工从浏览器复制后用 `--cookie` 传入**，工具不做交互式会话维持 |
| `/api/graphql` | 需 POST 查询 | 同上，已可提交 |
| `/admin` 后台（弱口令） | 需登录表单 POST + 会话保持 | 同上 |
| 字体反爬 / CSS 乱序 | 走 JSON 接口直接拿原文，没触发 | 无需还原 |

## 八、风控复盘：这次哪里没做好

终局审计（`/range/scoreboard`）：

| 请求数 | 被拦 | UA 数 | 路径数 | 跨度 | QPS | 最高风险分 |
|---|---|---|---|---|---|---|
| 1335 | 45 | 5 | 613 | 1646s | **0.81** | **45**（起始 30） |

- 被拦的 45 次几乎全部是 BFS 自动发现的 `/api/book/*`（428 挑战），**不影响核心数据**。
- **教训**：章节批量阶段用 `sleep 0.1` 串行，以为很慢，实际 QPS 仍有 0.81，风险分被抬到 45。
  正确做法是**直接约束 QPS 而不是约束单次间隔**——这正是 v3.9 `--qps` 要解决的问题。
- **另一个教训**：UA 换了 5 个、路径散了 613 个，风险画像很难看。真实对抗里应该
  **固定一套指纹、收窄路径范围、把 QPS 压到 0.3 以下**。

## 九、v3.9 针对这次实战补的能力

| 这次暴露的痛点 | 新增参数 | 一句话用法 |
|---|---|---|
| 499 个 URL 要启 499 次进程 | `--url-file 清单.txt` | 一行一个地址，配合 `-d 0`，一次进程抓完 |
| QPS 压不住，风险分被抬高 | `--qps 2` | 全局每秒请求上限，与线程数无关 |
| 撞上 JS 挑战 / 登录 / GraphQL 没法提交 | `--method POST --data "a=1"`、`--json '{...}'` | 表单与 JSON 两种请求体 |
| 被拦了还得翻页面清单慢慢猜 | （自动）`challenges.txt` | 428/429/418 与"403+挑战词"自动单列 |
| 想只抓本站、不想跟到外网 | `--same-host` | 把待爬队列限制在种子主机 |
| 同机多端口靶场互相引用 | `--extra-domain 127.0.0.1:3000` | 把其他端口标记为站内 |
| sitemap 种子吃光预算却不说 | （自动）告警 | 提示加 `--no-sitemap` 或调大 `--max-pages` |

## 附：给新手的三句话方法论

1. **先侦察后动手**：robots、sitemap、RSS、前端 JS、备份文件——把站点免费交出来的信息拿完，
   比闷头暴力爬高效十倍，也不容易触发风控。
2. **被堵就换通道，别硬撞**：移动端、老版本接口、开放平台、导出功能，鉴权往往是后补的。
   判定"这条路在工具能力内走不通"之后，要果断转向，而不是反复重试把风险分刷上去。
3. **把 QPS 当第一指标**：风控看的是请求速率与行为画像，不是单个请求乖不乖。
   宁可慢一点，也不要在审计板上留下 45 分。
